# Випуск застосунку для комп'ютера

> **Архітектура оболонки: ВШИТА збірка.** `frontendDist` — тека `../dist`, а
> не адреса. З цього випливає відповідь на питання, яке інакше має дві
> однаково правдоподібні відповіді: **service worker у вікні застосунку НЕ
> реєструється** (`ReloadPrompt.svelte`). Він закешував би вшиту оболонку й
> віддавав її після того, як оновлювач поставить нову версію — застосунок
> оновився, а показує стару збірку.
>
> У протилежної архітектури (оболонка возить сторінку з мережі, як
> `AudioRemote`) правильна відповідь протилежна: там воркер і є шляхом
> оновлення. Канон називає обидва випадки — `PWA-NO-SW-IN-SHELL`.

Встановлений HotPaste оновлюється сам: він питає `latest.json` у GitHub
Releases, звіряє підпис і ставить нову версію. Щоб це працювало, потрібна пара
ключів — і зроблена вона рівно один раз.

Доки ключа немає, все інше вже на місці й нічого не ламає: локальна збірка
працює, застосунок запускається, просто на кожну перевірку оновлень отримує
відмову й переходить на запасний шлях — каже, що вийшла нова версія, і відкриває
сторінку завантаження.

## Один раз: ключі

### 1. Згенерувати пару

```bash
npm run tauri signer generate -- -w "$HOME/.tauri/hotpaste.key"
```

> Команда інтерактивна — вона двічі спитає пароль. Запускайте її самі в
> терміналі: ключ підпису не має проходити через чужі руки, зокрема через
> журнал помічника.

Команда попросить пароль і надрукує дві речі:

- **приватний ключ** — у файлі `~/.tauri/hotpaste.key`. Він ніколи не потрапляє
  в репозиторій. Хто має його, той може випустити оновлення, яке встановиться
  людям на комп'ютери;
- **відкритий ключ** — надрукований у консоль, рядок на кілька сотень символів.

> Зробіть копію приватного ключа й пароля в надійному місці. **Загубити їх —
> означає втратити канал оновлення назавжди**: застосунки, які вже стоять у
> людей, приймуть оновлення тільки з підписом цієї пари. Полагодити це можна
> лише новою установкою руками на кожній машині.

### 2. Вставити ВІДКРИТИЙ ключ у репозиторій

У `src-tauri/tauri.conf.release.json` замінити `ЗАМІНІТЬ_ЦЕ_НА_ВІДКРИТИЙ_КЛЮЧ`
на надрукований відкритий ключ. Це публічне значення — воно й мусить лежати в
репозиторії.

### 3. Покласти ПРИВАТНИЙ ключ у секрети

Двома командами, без клацання в браузері. Перша читає файл, друга спитає
пароль і не покаже його на екрані:

```bash
gh secret set TAURI_SIGNING_PRIVATE_KEY -R Alik532UA/HotPaste < "$HOME/.tauri/hotpaste.key"
```

```bash
read -rs -p "Пароль ключа: " KEY_PW && printf '%s' "$KEY_PW" | gh secret set TAURI_SIGNING_PRIVATE_KEY_PASSWORD -R Alik532UA/HotPaste && unset KEY_PW && echo OK
```

> Друга команда працює в Git Bash. Якщо ви в PowerShell — простіше зробити
> цей один секрет у браузері: **Settings → Secrets and variables → Actions →
> New repository secret**, ім'я `TAURI_SIGNING_PRIVATE_KEY_PASSWORD`.

Перевірити:

```bash
gh secret list -R Alik532UA/HotPaste
```

Має бути рівно два рядки.

## Кожен випуск

```bash
git tag v0.2.0
git push origin v0.2.0
```

Далі робить [release.yml](.github/workflows/release.yml): проганяє гейти,
збирає інсталятор, підписує його й публікує разом із `latest.json`.

**Тег мусить збігатися з версією в `package.json`.** Вона підтягується в
`tauri.conf.json` і `Cargo.toml` автоматично (pre-commit хук), і саме її
порівнює встановлений застосунок. Тег `v0.2.0` при версії `0.1.72` дасть реліз,
який ніхто не отримає: версія в `latest.json` не буде новішою за встановлену.

Якщо ключів немає або в конфігу лишилася заглушка — прогін падає **першим
кроком**, за секунду, і пише, чого саме бракує. Це навмисно: без цієї перевірки
збірка йшла б двадцять хвилин і впала б на підписі з повідомленням, у якому не
видно, що робити. А гірший випадок — реліз опублікувався б із заглушкою замість
ключа, виглядав би повним, і жоден застосунок не прийняв би оновлення.

## Як перевірити, що канал справді працює

Зсередини репозиторію це не перевіряється — потрібні дві версії й жива машина.

1. поставити випущену версію з інсталятора;
2. випустити наступну (підняти версію, новий тег);
3. відкрити застосунок: за кілька секунд має зʼявитися вікно **«Завантажити та
   встановити»**.

Якщо кнопка каже **«Відкрити сторінку завантаження»** — канал не піднявся, і
застосунок про це чесно каже. Дивитися в журнал: рядок `Updater unavailable`
називає причину.

---

## Що перевіряється автоматично

`src/release.test.ts` тримає ланцюг цілим: плагін зареєстрований у Rust, дозвіл
`updater:default` є у можливостях, адреса `latest.json` указана, артефакти
вмикаються саме в накладці, workflow кладе `latest.json` у реліз і пакує бойовий
бінарник (у `Cargo.toml` типовий — `HotPaste-dev`).

Кожна з цих ланок при поломці **нічого не ламає видимо**: застосунок
запускається, працює, просто ніколи не оновлюється. Дізнатися про це без гейта
можна було б через місяці.

Єдине, чого перевірити не можна, — що відкритий ключ відповідає приватному з
секретів. Це видно лише на машині, яка приймає оновлення.
